# 완성된 제품 UI와 개발 과정을 함께 가져오기

> **후속 결정:** 이 문서는 초기 조사 기록이다. 개발 중 사용할 정형화된 완성 템플릿 하나를 선택한다는 목적에 맞춰, 현재 추천을 **Ant Design Pro full**로 수정했다. [실제 화면과 수정 이유](2026-11-06-template-choice.md)를 먼저 읽는다. 아래 공개 소스에 관한 사실은 초기 조사 근거로 보존한다.

**작성일: 2026-11-06**  
**근거 범위:** 공개 공식 문서, 공개 저장소의 실제 소스, 명시적으로 구분한 사용자 경험담. 대상 제품에 설치하거나 이식한 실측 결과는 포함하지 않는다.

## 1. 이번에 해결하려는 문제

제품 소유자가 반복해서 정보의 순서, 여백, 항목 구분, 버튼 여부, 반응형 배치와 갱신 동작을 지적해야 하는 상황을 줄이고 싶다. 목표는 독창적인 외형보다, 이미 잘 해결된 업무 화면과 동작을 재사용해 일관되고 편한 제품을 만드는 것이다.

재사용할 단위는 **목록에서 검색하고 항목을 열어 수정한 다음 원래 작업으로 돌아오는 전체 흐름**이다. 그 흐름에는 레이아웃, 데이터 연결, 상태 보존, 로딩·오류·갱신 처리, 모바일 동작이 포함된다. 색상과 컴포넌트만 가져오면 이 결정 대부분이 다시 구현자의 몫으로 남는다. 이 문서의 선택은 그 부담을 줄이는 방향의 기술적 판단이다.

## 2. 현재 선택

**운영·자원 관리 화면은 React-admin / ra-core 생태계를 우선 대상으로 한다. 구체적인 기준 구현은 Atomic CRM의 실제 화면과 Shadcn Admin Kit다.** 이 선택은 이번에 비교한 후보 중 동작하는 제품과 제품 전용 개발 절차를 함께 확인할 수 있었다는 이유에 따른다. 모든 제품에 가장 좋은 UX라는 비교 실험의 결론은 아니다.

확인한 근거는 다음과 같다.

| 필요한 것 | 기존 구현에서 확인한 내용 | 남는 일 |
| --- | --- | --- |
| 연결된 목록·상세·편집 | Atomic CRM에 실제 연락처·회사·업무·거래 화면이 있고, Shadcn Admin Kit가 ra-core와 연결된 목록·표·폼을 제공한다. [F1][F2] | 대상 업무의 데이터와 행동을 기존 흐름에 대응시킨다. |
| 갱신과 초기화의 구분 | ra-core의 `useRefresh`는 쿼리를 무효화한다. 목록 컨트롤러는 이전 데이터를 유지하는 옵션을 사용한다. [F3][F4] | 대상 앱이 별도로 화면을 제거하거나 상태를 초기화하지 않도록 통합한다. |
| 검색·정렬·페이지 상태 | React-admin 목록은 매개변수 저장과 URL 연결을 제공한다. 현재 소스는 명시적 `storeKey`에 따른 선택 상태 분리도 지원한다. [F4][F5] | 화면별 식별자와 어떤 동작에서 초기화할지를 연결한다. |
| 실제 제품의 갱신 처리 | Atomic CRM의 갱신 훅은 쿼리 갱신을 기다리고 중복 실행을 막는다. 목록에는 항목 ID 기반 렌더링과 선택·이동 코드가 있다. [F6][F7] | 자체 API, 데이터 변화와 화면 구조에서 동작을 확인한다. |
| 새 기능을 개발하는 과정 | Atomic CRM은 제품에 맞춘 에이전트 개발 절차와 실제 컴포넌트·리소스·데이터 계층을 지정하는 프런트엔드 참고 파일을 함께 제공한다. [F8][F9] | 대상 제품의 대응 관계와 구현 경계에 맞게 적용한다. |

현재 Atomic CRM의 스택은 **React + Shadcn Admin Kit + Supabase**다. 기본 React-admin의 Material UI 화면과 같은 패키지라고 취급하면 안 된다. ra-core라는 기반을 공유하지만 표시 계층은 다르다. 실제 제품 전체를 쓰는 것, 화면 흐름을 옮기는 것, ra-core만 도입하는 것은 작업 범위가 다르다. [F1][F2]

기존 백엔드에 연결하려면 data provider를 구현하거나 조정한다. React-admin은 데이터 제공자 경계를 제공하므로 특정 백엔드 하나로 바꾸는 것이 필수 조건은 아니다. 다만 Atomic CRM의 업무별 API와 Supabase 연결을 다른 도메인으로 바꾸는 비용까지 사라지는 것은 아니다. [F10]

React-admin의 일반적인 쿼리 갱신과 목록 상태 관리는 MIT 라이선스의 무료 코어에서 제공한다. `@react-admin/ra-realtime` 같은 준비된 실시간 확장은 별도 유료 Enterprise 기능이다. 일반 갱신 오류를 해결하기 위해 그 구독이 필요하다는 뜻은 아니다. [라이선스와 기능 구분](framework-evidence.md#7-cost-and-licensing)

### 다른 후보를 우선으로 삼지 않은 이유

- **Refine:** 데이터와 라우팅을 연결하는 좋은 기반이지만 headless 성격상 화면 조립의 선택이 더 남는다. 현재 공식 Mantine 통합은 v5이므로, 임의의 최신 Mantine 앱에 바로 붙는다고 가정할 수도 없다.
- **Ant Design Pro / ProComponents:** 완성된 앱 틀과 밀도·열 설정·갱신 구분을 갖춘 강한 후보다. 표 중심 업무에 적합하다. 다만 Ant Design/Umi 구조 채택과 제품별 상세·편집·복귀 연결은 별도 결정이다.
- **Cloudscape:** 운영 도구의 표, 상세, 필터, 선호 설정, 갱신 패턴이 구체적이다. 서버측 조회·정렬·페이지·선택 연결은 애플리케이션 구현으로 남는다.

위 비교의 공식 문서, 실제 소스, 라이선스는 [관리 UI 근거 문서](framework-evidence.md)에 정리했다. 후보 수를 늘리는 것보다 실제로 이어진 작업 흐름을 얼마나 가져오는지가 선택 기준이다.

## 3. 전체 과정도 이미 있는 것을 가져올 수 있는가

### Atomic CRM: 완성제품에 붙은 개발 과정

공식 하네스 문서는 단순 변경과 복잡한 변경의 경로를 나누고, 계획·개발·검토·문서화·병합을 연결한다. 세션별 변경 확인과 되돌리기도 제공한다. 검토한 개요와 프런트엔드 참고 파일에는 반복적인 소유자 스크린샷 승인이 전제되어 있지 않다. [F8]

이 하네스는 **Claude Code용**이며 인증된 Claude 구독 또는 Anthropic API와 프로젝트 실행 환경을 전제로 한다. 풀스택 실행에는 로컬 Supabase도 필요하다. 다른 에이전트 환경으로 옮길 때에는 제품 코드 재사용과 별도로 실행 방식의 대응 작업이 필요하다. [F8]

더 중요한 것은 그 과정이 실제 구현을 지목한다는 점이다. 프런트엔드 참고 파일은 다음과 같은 제품 내 연결을 지정한다. [F9]

- 폼은 데이터 바인딩과 검증이 연결된 기존 admin 입력 컴포넌트를 쓴다.
- 새 리소스는 정해진 목록·상세·생성·편집 구조와 등록 지점에 연결한다.
- 생성과 편집은 공통 필드 구성을 공유한다.
- 조회와 갱신은 ra-core 또는 data provider 경계를 사용한다.
- 모바일 목록과 페이지는 이미 있는 대응 구현을 사용한다.

**따라서 제품의 실제 코드와 개발 방식을 함께 가져올 수 있다는 근거는 있다.** 역할 이름이나 지침 파일만 다른 앱에 복사했을 때 같은 결과가 나온다는 근거는 없다. 확인 범위는 하네스 개요와 프런트엔드 참고 파일이며, 모든 훅·계획·병합 경로를 실행해 검증하지 않았다. 다른 도메인의 정보설계를 사용자 개입 없이 정확히 끝낸다는 성능도 입증하지 못했다.

### Design OS: 준비와 소스 인계 과정

Design OS는 제품의 목적과 영역, 데이터 관계를 정리하고, 영역별 요구사항·샘플 데이터·타입을 만든 뒤 실제 React 컴포넌트와 구현 인계 자료를 출력한다. 구현 단계에서 제공된 컴포넌트를 다시 그리지 않고 연결하도록 안내한다. 준비에서 구현 인계까지의 구조는 조사한 과정 도구 중 가장 구체적이었다. [P1][P2]

그러나 상위 설계 단계에서는 UI를 새로 생성하며 색상·글꼴·셸·영역 구성을 사용자와 논의한다. 일부 승인 단계가 제거됐어도 모든 디자인 결정이 자동화된 것은 아니다. 상태 관리, 라우팅, 데이터 조회, 실행 가능한 테스트도 구현 단계의 일이다. 따라서 기존 완성품이 요구에 맞는 경우 Design OS를 반드시 사이에 추가할 이유는 없다. [P2][P3]

**결론:** 이미 있는 구현을 우선 채택하고, 부족한 준비·인계 산출물은 기존 과정의 형식을 참고할 수 있다. 이 조합을 범용으로 검증된 자동 디자인 시스템이라고 부를 근거는 아직 없다. Superdesign, Agent OS, OOUX/ORCA의 범위와 사용자 개입은 [과정 근거 문서](process-evidence.md)에 비교했다.

## 4. 실제 화면을 만들기 전에 누가 무엇을 정리하는가

아래는 확인한 구현을 대상 제품에 적용하기 위한 **제안**이다. 특정 프로젝트가 이 전체 절차의 성공을 입증했다는 뜻은 아니다. 준비 작업은 구현 에이전트가 현재 요구·기존 코드·동종 제품을 읽고 수행한다. 제품 소유자가 화면마다 배치와 여백을 결정하는 절차를 만들지 않는다.

| 단계 | 구현자가 준비할 결과물 | 기존 구현과 연결되는 지점 |
| --- | --- | --- |
| 업무와 데이터 파악 | 사용자가 관리하는 대상, 대상의 관계, 자주 하는 행동, 즉시 필요한 정보, 숨겨도 되는 상세 | 목록·상세·폼의 리소스와 필드 |
| 전체 흐름 선택 | 목록→상세→수정→복귀 또는 다른 기존 업무 흐름 하나, 재사용할 소스 경로 | 앱 셸·라우팅·목록 컨트롤러·폼·모바일 변형 |
| 실제 데이터 대응 | 필드·행동·API의 대응표와 긴 이름·빈 값·오류·대량 항목 등의 대표 데이터 | data provider, 공통 입력과 표시 컴포넌트 |
| 기존 코드 연결 | 기준 구현의 화면과 상태 모델을 유지하면서 도메인 데이터를 연결한 실행 결과 | 기존 컴포넌트와 상태 소유 지점 |
| 작업 중 동작 확인 | 검색한 상태에서 편집·복귀, 화면 중간에서 자동 갱신, 입력 중 갱신, 느린 응답 등 실제 시나리오 | 대상 제품의 브라우저 실행과 필요한 회귀 검증 |

이 과정에서 디자인의 정답을 코드가 전부 대신 결정하지는 않는다. 예를 들어 어떤 속성이 중요하고 어떤 기능이 별도 메뉴를 가질지는 업무를 해석해야 한다. 그 판단은 구현자가 맡고, 기존 구현의 근거와 연결한다. 업무 의미 자체가 충돌하는 경우와 취향 선택을 구분한다.

### 나중에 추가되는 기능의 예

다음은 가상의 멤버 관리 화면이다. 새로운 요구를 먼저 기존 대상의 속성·행동·관계·독립 업무 중 어디에 해당하는지 대응시키면, 모든 요구가 새 버튼이나 새 페이지로 늘어나는 것을 줄일 수 있다.

| 추가 요구 | 업무상 의미 | 적용 제안 |
| --- | --- | --- |
| 최근 접속 시각 표시 | 멤버의 속성 | 목록의 보조 열 또는 상세 필드로 연결 |
| 역할 변경 | 멤버에게 하는 행동 | 기존 행 작업 또는 편집 폼에 연결 |
| 여러 멤버의 역할 일괄 변경 | 선택한 집합에 하는 행동 | 기존 선택·일괄 작업 흐름에 연결 |
| 월별 초대 추세 | 집계 정보 | 기존 개요 화면의 집계 영역에 연결 |
| 접근 권한 변경 이력 | 멤버와 관련된 기록 | 상세 화면의 이력 영역으로 연결 |

이는 해당 도메인을 확인하기 전의 예시다. 모든 기능을 이 표의 형태로 고정하자는 규칙은 아니다. 별도 탐색·권한·작업 목적이 생기면 독립 화면이 필요할 수 있다. 중요한 것은 새 요구가 기존 모델과 어떤 관계인지 해석하고, 이미 연결된 화면 흐름을 확장하는 것이다.

## 5. 자동 갱신과 버벅임은 별도로 확인할 구현 문제다

데이터 갱신, 페이지 이동, 필터 변경, 화면 진입은 서로 다른 동작이다. 실제로 React-admin은 쿼리 갱신을 제공하고, ProTable은 일반 재조회와 초기화를 구분한다. Cloudscape의 공식 갱신 패턴도 갱신 중 기존 데이터를 계속 보여주고 조작할 수 있게 하도록 설명한다. [F3][F11][F12]

그 구현을 채택해도 상위 앱이 레이아웃을 제거하거나 매번 다른 식별자로 다시 생성하면 상태가 손실될 수 있다. 항목 삭제·재정렬·높이 변화 역시 보이는 위치에 영향을 준다. 따라서 “특정 라이브러리가 모든 스크롤 문제를 자동 해결한다”고 말할 수 없다.

성능 역시 같은 데이터, 기기, 동작에서 측정해야 한다. 페이지네이션과 가상화는 대량 항목의 렌더링 부담을 줄이는 수단이지만, 메뉴를 열 때의 동기 작업이나 반복적인 전체 화면 재생성을 모두 해결하지는 않는다. 이번 조사에서는 후보 간 동일 조건 성능 비교를 수행하지 않았다. [세부 근거와 한계](framework-evidence.md#4-virtualization-and-responsiveness)

검증은 구현자가 수행해야 한다. 사용자가 불완전한 스크린샷을 반복 승인하는 절차로 이 동작 검증을 대신할 수는 없다.

## 6. 기존 디자인 문서는 어떻게 다루는가

**전체 폐기보다 업무 정의를 보존하고 구현 선택을 정리하는 편이 타당하다.** 이는 적용 제안이다.

| 문서 내용 | 처리 방향 |
| --- | --- |
| 데이터의 의미, 단위, 권한, 업무 관계, 필요한 행동 | 유지한다. 새 UI에도 필요한 제품 지식이다. |
| 실패한 사례와 재현 조건 | 실제 작업 시나리오와 연결한다. 특히 상태 손실·입력 손실·갱신 문제를 남긴다. |
| 예전 레이아웃·렌더링 방식·기술 제약에 대한 결정 | 현재 채택 결정과 충돌하는 범위를 명시해 대체한다. 과거 기록은 보관한다. |
| 한 번의 지적을 보편적 금지로 확대한 규칙 | 원래 해결하려던 업무 문제를 확인하고 적용 범위를 줄이거나 폐기한다. |
| 같은 요구를 중복해 적은 여러 문서 | 현재 선택과 구현 위치를 가리키도록 정리한다. |

완성된 외부 UI를 채택하려면 빌드와 의존성 정책도 그 채택을 허용해야 한다. 백엔드의 기술 선택과 프런트엔드 빌드 도구의 선택은 분리할 수 있다. 다만 실제 변경 범위는 각 제품의 배포·보안·유지보수 제약을 확인한 뒤 정한다.

## 7. 적용 경계와 다음 연구

장문 집필 화면은 문서 정체성, 커서, 한글 조합, 실행 취소, 오프라인 변경을 유지해야 한다. 관리 목록의 상태와 다른 문제이므로 관리 프레임워크를 그대로 적용할 대상으로 보지 않는다. ProseMirror는 문서·선택·트랜잭션 모델을 제공하지만, 그 위의 완성된 집필 제품 전체를 제공하는 것은 아니다. [F13]

이번 조사에서 확보한 것은 **관리 화면의 구체적인 기준 구현, 제품에 붙은 개발 절차, 준비·인계 도구의 범위와 한계**다. 후속 연구에서 결론을 바꿀 수 있는 질문은 다음 세 가지다.

1. 기준 구현을 다른 도메인의 실제 API와 연결했을 때 목록·상세·수정·복귀·갱신을 얼마나 그대로 유지할 수 있는가?
2. 새 필드와 새 업무 흐름을 추가했을 때 소유자의 디자인 판단 없이 기존 구조를 자연스럽게 확장할 수 있는가?
3. 집필·편집 작업에는 어느 공개 완성제품이 라이선스와 기술 조건을 충족하면서 비교 가능한 기반이 되는가?

이 질문은 구현자가 조사하고 검증할 과제다. 현재 공개 자료만으로 범용 무인 설계나 최고 수준의 사용성을 입증했다고 주장하지 않는다.
